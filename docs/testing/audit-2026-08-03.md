# LIF2TIFF 隔离审计报告（2026-08-03）

## 结论

当前 Linux GUI 和 conversion core 已具备继续人工验收的基础。常规真实数据、公开的
2D/T/Z/ZT/mosaic 样例以及一个实际转换均通过。审计发现并修复了一个“派生图像没有
acquisition timestamp 时整个 LIF 无法打开”的兼容问题。

目前没有发现会静默覆盖原始 LIF 或完整输出的路径。最应优先补强的不是图像读取，
而是 batch job 层：输出目录碰撞、目标磁盘可写性/空间、混合 resume，以及中途失败后
剩余任务的状态表达。

## 已修复问题

公开 FRET 文件中存在一个 Leica 派生 series：`FRET-Efficiency`。它没有 acquisition
timestamp，`liffile` 合理地返回 `None`，旧 adapter 却调用 NumPy datetime formatter，
导致整个文件 preflight 失败。现在仅在 timestamp 确实缺失时返回空列表；真实时间戳
的格式化逻辑未改变，并有回归测试。

为准备 PyInstaller，GUI、viewer、channel registry 和 plate calibration 的资源定位也已
兼容 frozen runtime，避免 Windows bundle 继续依赖源码目录。

## 未修改的已知缺口

### 优先级高：batch 输出安全检查

`A B.lif` 和 `A_B.lif` 都会被规范化为 `A_B_tiff`。当前两项各自 Dry Run 都可能显示
ready；真正转换时不会静默覆盖，但会出现“第一项完成、第二项失败”的半完成 batch。
人工复现文件位于 `manual_fixtures/output_collision/`，真实 54 个 GUI 测试文件中没有
发现这种碰撞。

建议在启动 batch 前一次性生成 job table，并拒绝重复的 canonical output path；同时
检查目标位置的最近现存父目录是否可写，以及可用空间是否高于估算输出加安全余量。

### 优先级中：resume 和失败恢复

Resume 目前是整个 batch 共用的 checkbox。因此，一个已有 `.partial` 的任务和一个
全新任务不能在同一批次启动。建议改为每个 job 自动判定 `new` 或 `resume`，冲突时才
要求用户选择。

某一项失败后，之前完成项是安全的，当前项会标为 Failed，但尚未开始的项仍可能显示
`Queued for conversion`。建议统一状态机为 `Ready / Running / Completed / Failed /
Cancelled / Not run`，并提供只重试 Failed + Not run。

### 优先级中：preflight 与实际启动之间的变化

GUI 保存的是 preflight 时的 channel confirmation，但 core 在转换开始时重新读取源文件。
如果 LIF 在这段时间被替换，channel index 可能与旧确认不一致。实验室正常操作中概率
低，但解决方式明确：启动前比较 size、mtime 和 metadata hash；变化则强制重新 preflight。

### 优先级低：交互和诊断

快速切换很多 LIF 时，旧 metadata worker 会继续完成读取，只是其结果会被 token 丢弃。
这不会写文件，但可能造成短时 CPU/I/O 峰值。后续可做 150-300 ms debounce，并限制
同时 metadata inspection 为 1-2 个。

非法 LIF 目前显示底层错误文本，技术上正确但不够友好。可在 GUI 增加“文件损坏、扩展名
错误或非 Leica LIF”的摘要，同时保留 Details 查看原始异常。

## Windows 准备状态

`windows/` 已包含 pinned requirements、PyInstaller `onedir` spec、版本信息、PowerShell
构建脚本和验收清单。选择 `onedir` 是为了启动更快、Qt plugin 更容易诊断，也便于内部
研究环境排错。

Linux 不能产出可信的 Windows executable；PyInstaller 官方也要求针对目标 OS 分别构建。
因此当前状态是“可在 Windows 原生构建”，不是“Windows 版已验证”。参考：
[PyInstaller spec files](https://pyinstaller.org/en/stable/spec-files.html)、
[PyInstaller usage](https://pyinstaller.org/en/stable/usage.html)、
[Qt for Python deployment](https://doc.qt.io/qtforpython-6.8/deployment/deployment-pyside6-deploy.html)。

Windows 首轮必须在干净账户或 VM 中验证：Qt 启动、拖入文件/文件夹、中文和长路径、
2D/T/Z/ZT preview、batch Dry Run、小文件转换、cancel/resume、输出迁移校验，以及
Defender/SmartScreen。对外分发前还需补第三方 license notices；代码签名和 installer
可以等 portable folder 稳定后再做。

## 醒来后的建议测试顺序

1. 打开当前 Linux GUI，拖入多个真实 LIF；确认右侧 Tools dock 不再被长文件名撑宽。
2. 多选后一次接受建议，检查每个 LIF 的确认状态，再运行 batch Dry Run，不转换大文件。
3. 拖入 `manual_fixtures/output_collision/`；观察当前缺口，只看 Dry Run，先不要 Convert。
4. 拖入 `manual_fixtures/malformed/not_a_lif.lif`；确认队列显示 Error，程序保持可用。
5. 用 2-3 个小型真实 LIF 做一次完整 batch，再中途取消另一批，核对状态和 `.partial`。
6. 讨论是否先实现四项 batch hardening，再继续 LUT/export/report 等新功能。

## 2026-08-03 后续实现

输出命名和 batch 碰撞缺口已经按用户确认的设计修复：有效的人类可读字符得到保留，
stem 尾部空格/句点被清理，Windows 非法字符被替换，Windows 大小写等价目标会阻断
整个 batch。冻结版 547 个 LIF 名称检查无碰撞，完整回归为 96 passed、2 xfailed。

原来的 `A B.lif`/`A_B.lif` 人工样例现在输出不同目录；新的碰撞样例是
`Sample.lif`/`sample.lif`。目标父目录可写性、单任务磁盘空间和同一文件系统的 batch
汇总空间检查随后也已补齐；当前完整回归为 101 passed、1 xfailed。剩余 xfail 是同一
batch 混合 new/resume。
